# Data card

This card describes the dataset convomem-arena serves, [Salesforce ConvoMem](https://huggingface.co/datasets/Salesforce/ConvoMem), as this environment uses it. Facts about how ConvoMem was built come from its paper ([arXiv:2511.10523](https://arxiv.org/abs/2511.10523)); the quality findings come from our own audit with the [data quality checker](data-quality.md).

## At a glance

| | |
|---|---|
| **Source** | `Salesforce/ConvoMem` on Hugging Face, pinned to revision `e3e9b39115b02346824c70d349350de738f8be41` |
| **Size** | 75,336 question–answer items (paper, Table 2) |
| **Personas** | 100 synthetic professionals (checked: 100 filler files), mostly enterprise roles |
| **Filler** | 400 unrelated conversations per persona (checked on a sample of personas) |
| **Generated by** | LLMs, "primarily Gemini and GPT-4", choosing a model family at random at each step (paper, §2.3.1) |
| **Validated by** | GPT-4o-mini and Gemini Flash (paper, Appendix A.2) |
| **Licence** | CC-BY-NC-4.0: non-commercial use only. The judge prompts and mixing code convomem-arena ports are Apache-2.0 |
| **Audit** | 368 items from 62 personas: **79% unflagged, under 1% structurally broken**; review flags point to a few real validity problems (below) |

## Composition

| Category | Items | Evidence conversations per item |
|---|---|---|
| `user_facts` | 16,733 | 1–6 |
| `assistant_facts` | 12,745 | 1–6 |
| `changing_facts` | 18,323 | 2–6 |
| `abstention` | 14,910 | 1–3 |
| `preferences` | 5,079 | 1–2 |
| `implicit_connections` | 7,546 | 1–3 |

Item counts are from the paper (Table 2); 36,860 items have one evidence message and 38,476 have several. Every conversation, evidence and filler alike, is synthetic. Speakers are labelled `User` and `Assistant` (mixed case in the raw files, normalised by convomem-arena). One generated conversation is about 6,000 characters, roughly 1.5k tokens.

## How it was made

The paper describes an evidence-first pipeline (§2.3.3 and Appendix A):

1. **Personas**, such as IT administrators and financial analysts.
2. **Use cases** per persona, each with a natural user question.
3. **Evidence cores**: each use case becomes a question, an answer and the evidence messages that support it, all from one speaker.
4. **Conversations**: the evidence is embedded in full conversations, the Nth evidence message in the Nth conversation. Filler conversations are generated "using identical methods".

Validation (Appendix A.2) checks the evidence count and speakers, that each evidence message appears exactly once in its conversation, and that a validator model answers correctly **with** the evidence conversations and fails **without** them, twice in a row. Category-specific checks require the latest update to matter for changing facts, and use rubrics for preferences and implicit connections. The paper reports that fewer than 5% of generated examples passed every check.

## What our audit found

We ran the [data quality checker](data-quality.md) on 368 items sampled across 62 personas, every category and every evidence-count folder, with filler checked for 25 of those personas. Then we read every flag by hand.

| Finding | Items | What it means |
|---|---|---|
| No flags at all | 290 of 368 (79%) | — |
| **Structural errors** | 3 | one implicit-connections item with two evidence messages in a one-evidence folder (its conversation count is off too); one abstention item whose evidence matches its conversation at only 0.82 similarity |
| Evidence present only in reworded form | 11 | the conversation generator changed an evidence message's opening; the fact itself is intact. Harmless |
| A number in the answer is not in the evidence | 27, mostly `user_facts` (24% of them) | almost all are **computed answers**: sums, totals and averages over several evidence messages |
| A name in the answer is not in the evidence | 23 | mostly harmless (headings, acronyms, the user's own name), but **one answer relies on world knowledge**: it recommends a city and a museum the history never mentions |
| Changing facts: the latest evidence is not the best match | 9 of 75 | mostly answers that combine several updates; a few need a human look |
| The answer's names appear in unrelated filler | 13 of 224 checked | a mix of harmless repeats of the same fact, coincidences, and **true conflicts** |

The true conflicts matter most. In one `changing_facts` item the gold answer names Jessica as the new Head of Sales Ops, while the same persona's filler names Helen Vance as head of Sales Ops. Mixing places filler at random positions, so that filler can land *after* the evidence, and an agent that reports Helen Vance is then marked wrong for following the history it was given.

### Why these slip through

Each problem lines up with a step of the pipeline above:

- **Filler conflicts.** Filler is generated the same way as evidence conversations, for the same persona, but the paper describes no check of filler against other items' answers. Two independently generated conversations can disagree about the same person.
- **Computed and world-knowledge answers.** Validation asks a model whether the evidence lets it answer. A capable model can add up numbers or bring in outside knowledge and pass, so answers that the history alone does not state survive validation.
- **Reworded evidence.** The embedding check allows fuzzy matches, so an evidence message can enter its conversation in slightly different words.

## Using the data with these findings

- **Read `abstention` beside the fact categories, never alone.** "I don't know" stays correct when evidence is missing, so abstention can look perfect even when memory is failing.
- **Treat `user_facts` partly as an arithmetic test.** Nearly a quarter of sampled `user_facts` answers are computed. A low score there can be arithmetic, not memory.
- **Expect a small noise floor from filler conflicts.** In the sample, about 1% of the fact items checked had filler that truly disagreed with the gold answer.
- **Keep the judge fixed** across compared runs, and check it with the [judge robustness checker](judge-robustness.md): local judges graded the reply against the gold answer but never noticed a negated question.
- **For a cheap, stable fact score**, use [exact match](../concepts/scoring.md#exact-match-for-fact-categories). It agreed with the judge on every judged reply we checked.
- **Comparable in protocol, not item for item.** convomem-arena draws its own samples with ConvoMem's official mixing rather than the pre-mixed test cases, so scores follow the paper's protocol but are not the paper's exact items.
- **Non-commercial only.** CC-BY-NC-4.0 rules out commercial use, including training a commercial model on it.

## Reproducing the audit

```bash
python -m convomem_arena.data_check --out outputs/data-check/run1
```

It samples the same way by default (5 persona files per folder, 3 items each, filler for 25 personas, seed 0) and writes `report.md`, `flags.jsonl` and `review.md`. Larger `--files-per-folder` and `--items-per-file` values audit more, up to the whole dataset.
